\section{Design \& Architecture}

\subsection{High-Level Structure}

The project is intentionally split into two layers:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Shell entry and persistence layer.} \texttt{main.sh} authenticates two players, registers new users when needed, and launches the Python application with the chosen usernames. \texttt{leaderboard.sh} reads persistent history from \texttt{history.csv} and prints a sortable terminal leaderboard.
    \item \textbf{Python game engine layer.} \texttt{game.py} owns the graphical menu, game selection, result recording, chart generation, and post-game flow. The individual games live under \texttt{games/} and inherit shared behavior from \texttt{games/base\_game.py}.
\end{enumerate}

This split was a deliberate design choice. Authentication and leaderboard reporting map naturally to Bash scripts and text files, while the interactive board games themselves are better handled in Python with Pygame and NumPy.

\subsection{Core Components}

\paragraph{Authentication and launch flow.}
The program starts in \texttt{main.sh}. It ensures \texttt{users.tsv} exists, hashes passwords, enforces that Player 1 and Player 2 are different users, and then launches \texttt{game.py} with two validated usernames. This gives the rest of the system a clean contract: once Python starts, it can assume the players are already authenticated.

\paragraph{Game hub orchestrator.}
\texttt{game.py} is the main controller. It:

\begin{itemize}[leftmargin=*]
    \item shows the menu of available games and leaderboard sort options,
    \item launches the selected game object,
    \item records results to \texttt{history.csv},
    \item calls the Bash leaderboard,
    \item generates a Matplotlib chart image, and
    \item shows a post-game screen with summary cards and replay/quit options.
\end{itemize}

The advantage of this central controller is that each individual game class stays focused on its own rules and rendering, while the hub owns cross-cutting concerns such as history, analytics, and session flow.

\paragraph{Shared board-game base class.}
\texttt{games/base\_game.py} provides the common state used by all board games:

\begin{itemize}[leftmargin=*]
    \item player names,
    \item current turn,
    \item a NumPy board array,
    \item reset/turn-switch helpers, and
    \item a shared one-step undo snapshot mechanism.
\end{itemize}

Adding undo here was especially useful because the same pattern was needed across Tic-Tac-Toe, Connect Four, and Othello. By storing the last board state and a small amount of extra per-game metadata, the games can each offer one-step undo without duplicating the full snapshot infrastructure.

\paragraph{Game modules.}
Each game module combines game-specific rules with its own Pygame rendering code:

\begin{itemize}[leftmargin=*]
    \item \texttt{tictactoe.py}: 10x10 board, five-in-a-row win condition, human-vs-human mode, and a single-player engine mode.
    \item \texttt{connect4.py}: 7x7 gravity-based placement, animated drops, and four-in-a-row detection.
    \item \texttt{othello.py}: legal move scanning in eight directions, disc flipping, pass-turn handling, and end-game score comparison.
\end{itemize}

\paragraph{Persistent data and reporting.}
Two text files provide simple persistence:

\begin{itemize}[leftmargin=*]
    \item \texttt{users.tsv} stores usernames and password hashes.
    \item \texttt{history.csv} stores winner, loser, timestamp, and game name for each completed match.
\end{itemize}

This file-based approach is lightweight, easy to inspect during development, and sufficient for a small local game hub. It also keeps the Bash analytics straightforward because the leaderboard can operate directly on CSV rows.

\subsection{Key Design Decisions and Rationale}

\paragraph{NumPy boards instead of nested Python lists.}
Using NumPy for every board gave the project a consistent representation and made the rule checks cleaner. Tic-Tac-Toe and Connect Four particularly benefit because they need repeated pattern detection over a grid. Vectorized operations made those checks concise and less error-prone than manual loops over every possible segment.

\paragraph{Heuristic engine instead of minimax.}
The single-player Tic-Tac-Toe mode uses a scoring heuristic instead of a full minimax search. That was a practical tradeoff: on a 10x10 board with a five-in-a-row target, a simple heuristic that prioritizes wins, blocks, and central control gives responsive play without introducing expensive search logic or a noticeable UI delay.

\paragraph{Matplotlib rendered to file, then loaded into Pygame.}
Pygame and Matplotlib do not naturally share the same live UI pipeline. We therefore render charts using Matplotlib's non-interactive \texttt{Agg} backend, save the chart image to \texttt{stats.png}, and load that image inside the Pygame post-game screen. This separation avoids event-loop conflicts and keeps chart rendering deterministic.

\paragraph{Leaderboard kept in Bash.}
We intentionally did not move the leaderboard into Python, even though that would have been possible. Keeping it in Bash preserved the mixed-language nature of the assignment and gave the shell portion a meaningful job beyond startup scripting. The final version also handles game names with spaces correctly, which mattered once \texttt{Connect Four} and \texttt{Tic-Tac-Toe} both appeared in the same history file.

\section{Features Implemented}

\begin{enumerate}[leftmargin=*]
    \item \textbf{Two-player authentication and registration.} Players can log in with existing credentials or register new accounts from the terminal. Passwords are stored as SHA-256 hashes rather than plaintext.
    \item \textbf{Protected two-user session flow.} The script prevents both players from logging in as the same username in the same session.
    \item \textbf{Graphical game selection hub.} After authentication, the Pygame menu allows users to choose between Tic-Tac-Toe, Tic-Tac-Toe vs Engine, Othello, and Connect Four.
    \item \textbf{10x10 Tic-Tac-Toe.} Supports human-vs-human play with five-in-a-row win detection across horizontal, vertical, diagonal, and anti-diagonal directions.
    \item \textbf{Single-player Tic-Tac-Toe engine mode.} One player can challenge the computer. A dedicated selection screen lets either authenticated user choose to play against the engine.
    \item \textbf{Connect Four.} Implements gravity-based placement, animated coin drops, a hover indicator, and vectorized four-in-a-row detection.
    \item \textbf{Othello / Reversi.} Implements valid-move hints, disc flipping, skipped turns when a player has no legal move, and end-of-game scoring.
    \item \textbf{One-step undo in every game.} Each game includes an on-screen Undo button and a keyboard shortcut, restoring the immediately previous move only.
    \item \textbf{Persistent match history.} Finished games append a row to \texttt{history.csv} with winner, loser, timestamp, and game name.
    \item \textbf{Terminal leaderboard.} The Bash leaderboard prints per-player per-game wins, losses, and win/loss ratios; supports sorting by wins, losses, or ratio; and displays total draw count in the footer.
    \item \textbf{Readable leaderboard layout.} The leaderboard uses a boxed table, separate game-name and metric rows, and correct handling of multi-word game names.
    \item \textbf{Post-game analytics.} The results screen shows a chart panel, top-winner summary, most-played-game summary, and total matches played.
    \item \textbf{Replay flow.} After a finished match, players can either return to the menu and play again or quit the application cleanly.
\end{enumerate}

\begin{itemize}[leftmargin=*]
    \item Python 3.10 or newer
    \item Bash shell
    \item \texttt{pygame-ce}, \texttt{numpy}, and \texttt{matplotlib}

\section{Usage}

\subsection{Running the Project}

From the repository root:

\begin{lstlisting}[language=bash]
source .venv/bin/activate
bash main.sh
\end{lstlisting}

The expected flow is:

\begin{enumerate}[leftmargin=*]
    \item Player 1 logs in or registers.
    \item Player 2 logs in or registers with a different username.
    \item The graphical menu opens.
    \item Players choose a game or inspect leaderboard sort options.
    \item After a game ends, the history file is updated, the terminal leaderboard is printed, and the Pygame post-game summary is shown.
\end{enumerate}

\subsection{Interaction Notes}

\begin{itemize}[leftmargin=*]
    \item \textbf{Tic-Tac-Toe / Othello / Connect Four}: mouse clicks place marks or discs.
    \item \textbf{Undo}: available through the on-screen button and keyboard shortcut.
    \item \textbf{Leaderboard preview}: the menu includes sort buttons that print the terminal leaderboard by wins, losses, or ratio.
    \item \textbf{Single-player mode}: the ``Tic-Tac-Toe vs Engine'' option asks which authenticated player wants to challenge the computer.
    \item \textbf{Exit flow}: after a finished match, players can either play again or quit from the results screen.
\end{itemize}

\section{Retrospective}

\subsection{Challenges and How We Addressed Them}

\paragraph{Mixed-language coordination.}
One recurring challenge was keeping the Bash and Python parts aligned. Authentication, result recording, leaderboard parsing, and the Pygame screens all depend on a shared understanding of usernames and history rows. We kept this manageable by standardizing the file formats early: tab-separated credentials in \texttt{users.tsv} and comma-separated game history in \texttt{history.csv}.

\paragraph{Rule checking without brittle nested logic.}
The grid-based games each had different rule complexity. Tic-Tac-Toe needed efficient five-cell scans on a large board, Connect Four needed directional checks that were not confused by player-value encoding, and Othello required directional line scanning and pass logic. NumPy helped on the first two, while a clean directional helper approach kept Othello understandable.

\paragraph{Undo across multiple games.}
Undo sounds simple, but each game also carries small amounts of metadata beyond the board itself. For example, Othello needs to restore skip-delay state and Tic-Tac-Toe needs to clear engine-thinking state. The shared snapshot system in \texttt{base\_game.py} solved the common part, while each game restored its own additional fields after an undo.

\paragraph{Readable statistics.}
The first statistics and leaderboard outputs were functional but not very readable. We iterated on both: the post-game chart was made more compact and presentation-friendly, and the terminal leaderboard was reformatted into a clearer boxed layout with a better header structure.

\paragraph{Handling game names with spaces.}
An unexpected shell-side bug came from using a \texttt{for} loop over game names. This split \texttt{Connect Four} into two separate tokens. We fixed that by reading unique game names line by line from a temporary file, which made the leaderboard robust for multi-word titles.

\subsection{What We Would Do Differently With More Time}

\begin{itemize}[leftmargin=*]
    \item Replace the plain CSV/TSV persistence with a lightweight database or structured JSON model.
    \item Record draws in a richer format so leaderboard reports can attribute draw counts to individual players instead of only tracking total draws.
    \item Expand automated testing for core rule logic, especially around Othello edge cases and engine behavior.
    \item Improve the single-player engine with deeper search or difficulty levels.
    \item Add richer visuals such as sound, transitions, and custom art assets while preserving responsiveness.
\end{itemize}
